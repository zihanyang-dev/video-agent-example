# 对照怎么做

`architecture.md` §0 说了要证明什么:**同一份 brief、同一批素材,哪边剪得更好、返工更少。**

这份文件说的是那句话怎么变成一次真的、能被别人重做一遍的测量。写在跑之前,不是跑完之后 ——
跑完再定口径,定出来的一定是自己赢的那个口径。

## 先说什么情况算我们输

写在最前面,因为一个证伪不了的论点不值得花三个人一个季度:

- **返工次数没有显著差别。** 论点是「真的命令行返工更少」。如果两边都是平均两轮收敛,那这套
  架构的复杂度就没有回报,该回去用工具。
- **单条成本高一个数量级。** 编排 token 只占 1–2%(§9),但如果 agent 会自己重复生成、把钱花在
  试错上,那省下来的人力是用生成费换的,而生成费是这个业务里最贵的一项。
- **失败方式更难收场。** 工具调用失败是一个已知的错误码;一条模型现编的命令失败,可能是任何东西。
  如果线上排查一次要比现在长得多,那对运维是净亏。

三条里中任意一条,结论就是「这条路不成立」,如实写进结论。

## 三件事必须钉死

**brief 不是我们写的。** 找一个既不做 pexo 也不做这个仓库的人写,一次写十条,写完封存。
我们自己写的 brief 一定会不自觉地挑对我们这边有利的题 —— 比如规格不一致的素材,那正好是
`concat` demuxer 的死穴。挑题就是作弊,而且是最不容易被自己发现的那种。

十条里要覆盖真实分布,不能全是难题:

| 类型   | 条数 | 例子                                     |
| ------ | ---- | ---------------------------------------- |
| 直给   | 4    | 三段素材接起来,加个标题,出 1080p         |
| 有约束 | 3    | 卡 15 秒;竖屏改横屏;配一段既有音轨的节奏 |
| 要判断 | 2    | 「剪得紧一点」「开头太平了」             |
| 没素材 | 1    | 全靠生成                                 |

**素材一样,模型也一样。** 两边都用 Seedance 2.0 / Seedream 4.5,同一批源片,同一个分辨率目标。
不一样的只有中间那层 —— 一边是切好的工具,一边是文件系统加命令行。**任何一边换模型,这次对照作废。**

**判片的人不知道哪条是哪边出的。** 两个 mp4 随机排序给他看,只问两个问题:哪条能直接用;
不能用的话,缺什么。判片的人不能是写这两套东西的任何一个人。

## 量什么

每条 brief 两边各跑一次,记六个数。前两个是主结论,后四个是解释它的:

1. **到验收的轮数。** 一个人从提出 brief 到说「这条能用」,一共说了几次话。**这就是「返工」,
   也是主指标。** 首轮就过 = 1。
2. **到验收的单条成本。** 生成费 + 编排 token 费,所有轮加起来。不是首轮成本 —— 返工的钱
   也是钱。
3. 到第一条能看的东西的墙上时间。人愿意等多久,取决于多久能看见第一个东西。
4. 到验收的墙上时间。
5. **出错几次、其中几次它自己爬起来了。** 这条最重要的不是次数而是比例:自己恢复的错误对用户
   是不可见的,对运维也是。
6. **人工介入几次。** 需要我们去看日志、去手动改一条命令的次数。这项在两边都必须是 0 才算
   「能上线」,不是 0 就单独列出来。

第 5 和第 6 项量的是同一件事的两面,**别合并**:一个从不出错但一出错就要人的系统,和一个经常
出错但都自己解决的系统,在这张表上必须长得不一样。

## 怎么记

一条 brief 一个 markdown,放 `docs/runs/<日期>-<brief 编号>-<哪边>.md`,六个数 + 每一轮的
原话 + 最终 mp4。**mp4 要留着**,因为「剪得更好」最后是眼睛判的,数字只能解释它,不能替代它。

一边跑完再跑另一边,不要交替 —— 交替的话第二次写 brief 的措辞会被第一次的结果带偏。

## 已经有的一半

一次真跑,只跑了这边,没有对照(§0):三个规格不一致的源片要一条 6 秒 montage,
**118 秒,8 次工具调用,1 次自己爬起来的错误,$0.0354**,抽帧核对过竖屏那条是加黑边不是拉伸。

按上面的表,这一条填了第 3、4、5 项,**第 1、2 项填不了,因为没有第二轮 —— 没有人验收过它。**
这正是「§0 只有一半」的准确含义:我们量了一次执行,没有量一次合作。
